# Phase 8 — Cancellation, Returns and Refunds

Status: Phase 8 COD after-sales workflow, owner-approved return-courier/recipient-verification rules and local QA are implemented. Production-host and real-money sign-off remain external release gates; bKash remains Coming Soon.

## Approved operating boundary

- Earthquick central admin owns customer-facing cancellation, return and refund decisions. No separate vendor portal or payout system.
- Delivery and order status remain order-wise. Returns and partial refunds must be able to reference individual order items without silently rewriting the original sale snapshots.
- bKash remains Coming Soon; no gateway or automatic refund is enabled.

## First slice: durable status history

- New orders create an initial `pending` history event in the same checkout transaction as the order and stock decrement.
- An admin status transition creates an event in the same transaction as the update, with previous/new status, admin user, timestamp and the supplied internal note. Editing courier details without changing status creates no duplicate status event.
- Admin order detail displays the recorded timeline. Older orders are **not** assigned invented historical events; the page says when no history exists.
- The migration `2026_09_27_110000_create_order_status_events_table.php` was applied only to the local `earthquick_db` after a verified 18-table pre-migration dump at `storage/qa/phase8-db-backup/earthquick_db_pre_phase8_2026-09-27.sql`. That SQL backup is ignored and contains private data. Production migration and browser sign-off remain pending.

## Second slice: pre-fulfillment COD cancellation

- Registered customers can request cancellation only for their own linked order. Guests can request only while their checkout session still authorizes that order. The request does not itself change the order or stock.
- Only unpaid COD orders in `pending` or `confirmed` can use online cancellation. A duplicate pending request is rejected. Admin can approve or decline with a recorded note, actor and timestamp; a rejected request leaves the order and inventory unchanged.
- The existing admin `cancelled` choice now uses the same atomic cancellation path, including approval of any pending request. It requires an internal reason. Cancelled orders cannot be reopened through the ordinary status form, and later fulfillment stages cannot be moved backward through that form to bypass cancellation eligibility.
- Approval changes the order to `cancelled`, changes unpaid COD to `not_due`, restores product or variant stock once, recomputes parent variant stock, decrements the original coupon's usage count once, and writes the status event. Missing or ambiguous inventory prevents approval and rolls back all changes. Paid or already-fulfilled orders cannot use this shortcut; they need the later refund/return flow.
- New checkout orders persist `coupon_id` as well as the existing human-readable coupon code. Cancellation uses the original ID, not a possibly reused code. Historical coupon orders without this identity stop for manual reconciliation rather than decrementing an unrelated coupon. Migration: `2026_09_27_130000_add_coupon_identity_to_orders_table.php`.
- The new `2026_09_27_120000_create_order_cancellation_requests_table.php` migration ran only on local `earthquick_db`, after a verified 19-table private dump at `storage/qa/phase8-db-backup/earthquick_db_pre_cancellation_2026-09-27.sql`. The coupon-ID migration likewise ran locally after a verified 20-table dump at `storage/qa/phase8-db-backup/earthquick_db_pre_coupon_identity_2026-09-27.sql`. No production migration or real-order cancellation was performed.
- Automated tests cover guest/account ownership, duplicate requests, admin authorization, approval/rejection, direct admin cancellation, coupon and variant restock, missing-variant rollback and paid/fulfilled-order guards. Browser QA of the new request/decision screens remains pending.
- `composer test` passes 125 PHP tests / 727 assertions and 10 frontend tests after this slice.

## Third slice: item-level return intake and review

- A customer can request a specific quantity from an order item only after the order is `delivered`, if the saved order-item snapshot says returnable and the saved return window has not expired. The window is counted from a recorded `delivered` status event, never guessed from order creation. Older orders lacking that evidence require manual support review.
- Account requests require exact order ownership; guest requests require the original checkout session. An item ID from another order is rejected. Pending, authorized and received quantities reserve capacity, so multiple requests cannot exceed the purchased item quantity; rejection releases capacity.
- Central admin can authorize or reject a pending request with an internal note and recorded actor/time. An authorized request is **not** a refund or inventory receipt. Admin separately confirms physical receipt with a note and actor/time; this still does not restock or refund the item. Duplicate decisions and receipts are rejected.
- Customer and admin order pages show item-level request states. Customer-facing copy distinguishes request, authorization, receipt and future refund review.
- Migration `2026_09_27_140000_create_order_return_requests_table.php` was applied only to local `earthquick_db`, after a verified 20-table private dump at `storage/qa/phase8-db-backup/earthquick_db_pre_returns_2026-09-27.sql`. No real order/return or production database was changed.
- `composer test` passed 129 PHP tests / 778 assertions and 10 frontend tests. Browser visual QA of the new screens remains pending.

## Final local slice: inspection, inventory and COD refund

- After physical receipt, central admin records exactly one inspection outcome: accepted/resellable, accepted/not resellable, or rejected. Inspection has a note, actor and time. Receipt or inspection never automatically changes inventory or pays a refund.
- Only an accepted/resellable item can be restocked, with an explicit confirmation. The original product/variant is validated and locked; missing or ambiguous inventory rolls back rather than silently changing another SKU. The restock audit prevents duplicate stock increments.
- For a delivered, paid COD order with an accepted return, admin approves one item-level refund record. The returned quantity uses the original unit-price snapshot. Order-wide discount is allocated by original item-price proportion, with cumulative cent rounding so all returned items together receive the exact original discount. Partial returns never refund delivery. Admin may include delivery once only when the final accepted return brings the entire order subtotal into the refund calculation.
- Refund approval records a calculated amount and audit note but **does not send money**. For a positive amount, the owner sends money outside Earthquick, then central admin explicitly confirms the actual transfer, method and unique external reference. Only this second action marks the refund completed. A zero-value refund is recorded as `no_refund_due` and cannot be marked paid. The customer page distinguishes pending review, approved/pending payment and actually paid.
- New local migrations: `2026_09_27_150000_add_return_inspection_fields.php` and `2026_09_27_160000_create_order_refunds_table.php`. They were applied only to local `earthquick_db` after verifying a 21-table SQL backup at `storage/qa/phase8-db-backup/earthquick_db_pre_refunds_2026-09-27.sql`. The backup contains private data, is ignored by Git and must not be published. No existing order or return record was modified by this work.

HTTP view tests do not replace browser visual QA.

## Owner-approved return courier and recipient policy

- The customer's reason category is a report, not the final decision. When authorizing a return, central admin records the verified category and a decision note. Verified wrong item or damaged/defective item assigns return courier postage to Earthquick; fit, change of mind and other reasons assign it to the customer. The customer sees the confirmed payer after authorization. A disputed or old uncategorized request needs manual review; no historical payer is fabricated.
- The original checkout delivery fee and the new return courier postage are different. The existing partial/full original-delivery-refund rule stays unchanged. If Earthquick owes return courier postage and the customer paid the courier, admin may add the verified receipt amount to the item's COD refund, with a unique courier receipt/tracking reference. If Earthquick booked/paid the courier directly, record zero reimbursement. Customer-paid or unverified returns cannot add postage automatically; a repeated receipt cannot be reimbursed twice. This postage is outside the original paid-order cap, while the sale refund remains capped at the order total.
- Recipient verification now precedes payment recording as a separate admin action on an approved refund. Admin records intended method, recipient name, transfer destination's last four digits (cash excepted), verification via the original order contact or in person, a note explaining any alternate recipient, actor and time. No full account/mobile destination field is stored. The action leaves the refund `approved`. Only after actual external payment can admin enter a unique transfer/cash reference and confirm the refund `completed`. The system records the declaration and audit trail, not independent bank proof.
- Migration `2026_09_27_170000_add_return_shipping_and_refund_recipient_audit.php` adds nullable policy/audit fields without backfilling historical decisions. It ran only on the local database after a verified 22-table private backup at `storage/qa/phase8-db-backup/earthquick_db_pre_return_policy_2026-09-27.sql`, and passed on the isolated MySQL rehearsal database. Do not publish the ignored backup.
